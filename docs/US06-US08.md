# PDF de entradas y recomendaciones

Implementación del backend de US-06 y US-08 siguiendo Controller → Service → Repository.
Se utilizan las tablas existentes. No se necesita recrear la base de datos ni ejecutar scripts SQL adicionales.

## Preparación

```powershell
dotnet restore EventosPeruIA.slnx
dotnet build EventosPeruIA.slnx
dotnet test EventosPeruIA.slnx --no-build
dotnet run --project EventosPeruIA.API
```

La API conserva la conexión SQL Server y la configuración JWT del proyecto. Las pruebas usan una base SQLite temporal en memoria y un servidor HTTP de pruebas; no acceden a la base de datos real. La traducción y los bloqueos específicos de SQL Server requieren una comprobación adicional con ese motor.

## US-06 Descarga de entradas

Todas las rutas requieren `Authorization: Bearer <token>` del comprador.

| Método y ruta | Resultado |
| --- | --- |
| `GET /api/Compra/mis-entradas` | Lista existente con `idEntrada`, estado, evento y código de entrada. |
| `GET /api/Compra/entradas/{idEntrada}/pdf` | PDF de una entrada. |
| `GET /api/Compra/{idCompra}/pdf` | PDF de la compra con un voucher por entrada. |

La respuesta exitosa es el archivo binario con `Content-Type: application/pdf` y `Content-Disposition: attachment`, no un objeto JSON. Los errores conservan `{ mensaje, datos }`.

- Se verifica la propiedad de la entrada/compra contra el `UserId` del JWT. Un recurso ajeno o inexistente devuelve 404.
- Solo se descargan entradas de compras pagadas o reembolsadas. Las compras pendientes/rechazadas no generan vouchers descargables.
- El voucher incluye evento, fecha y hora, dirección, asistente, número de compra/entrada, precio **pagado en la compra**, estado y QR.
- El QR codifica exactamente `CodigoEntrada` como GUID, compatible con `POST /api/CheckIn/validar`. Descargarlo no cambia el estado ni crea otra entrada.
- Las entradas anuladas y utilizadas se identifican expresamente en el PDF. El servidor de check-in sigue siendo la autoridad sobre su validez actual.
- Los archivos se generan en memoria; no se publican en una carpeta accesible por URL. La descarga responde con `Cache-Control: no-store`.
- `Content-Disposition` queda expuesto por CORS para que Vue pueda leer el nombre del archivo.

Ejemplo con la instancia Axios del frontend que ya adjunta el token:

```javascript
async function descargarEntrada(idEntrada) {
  const respuesta = await api.get(`/Compra/entradas/${idEntrada}/pdf`, {
    responseType: 'blob'
  })
  const url = URL.createObjectURL(respuesta.data)
  const enlace = document.createElement('a')
  enlace.href = url
  enlace.download = `entrada-${idEntrada}.pdf`
  document.body.appendChild(enlace)
  enlace.click()
  enlace.remove()
  setTimeout(() => URL.revokeObjectURL(url), 1000)
}
```

Si Axios usa una `baseURL` que no termina en `/api`, agrega ese prefijo. En el `catch`, un error recibido con `responseType: 'blob'` puede leerse con `await error.response.data.text()` y luego `JSON.parse` para mostrar `mensaje`.

El generador utiliza [QuestPDF](https://www.questpdf.com/quick-start.html) y [QRCoder](https://github.com/Shane32/QRCoder). La licencia Community de QuestPDF se configura una vez al iniciar la aplicación para este proyecto académico; véase su [guía de licencia](https://www.questpdf.com/license/guide.html).

## US-08 Intereses y recomendaciones

Todas las rutas requieren sesión. El usuario se obtiene del JWT: no se recibe un `idUsuario` editable desde el frontend.

| Método y ruta | Uso |
| --- | --- |
| `GET /api/Recomendacion/intereses` | Catálogo activo, lista de `{ idInteres, nombre }`. |
| `GET /api/Recomendacion/mis-intereses` | Selección actual en `datos`. Una lista vacía permite ofrecer la selección inicial. |
| `PUT /api/Recomendacion/mis-intereses` | Reemplaza la selección con `{ "idIntereses": [1, 2] }`. |
| `GET /api/Recomendacion` | Hasta seis tarjetas ordenadas, con título de sección y explicación individual. |

Se aceptan entre uno y cinco IDs distintos, existentes y activos. “Elegir después” consiste en omitir el PUT; puede guardarse la selección desde el perfil. La sustitución se hace en una transacción. Una cuenta suspendida no puede obtener ni modificar sus recomendaciones/intereses.

Ejemplo de respuesta de recomendaciones:

```json
{
  "mensaje": "",
  "datos": {
    "titulo": "Recomendado para ti",
    "esPopular": false,
    "tieneIntereses": true,
    "eventos": [
      {
        "idEvento": 1,
        "nombre": "Noche de Rock en Barranco",
        "categoria": "Concierto",
        "fechaHoraInicio": "2026-11-14T20:00:00",
        "departamento": "Lima",
        "distrito": "Barranco",
        "precio": 60.00,
        "precioTexto": "S/ 60.00",
        "cuposDisponibles": 190,
        "agotado": false,
        "imagenUrl": null,
        "motivo": "Porque te interesa Música. En tu departamento: Lima"
      }
    ]
  }
}
```

El frontend utiliza `datos.titulo` para el encabezado, `datos.eventos` para las tarjetas, `motivo` para explicar la recomendación e `idEvento` para navegar al detalle. Debe volver a consultar después de guardar intereses o completar una compra, y al regresar al inicio. El backend calcula cada respuesta con los datos actuales, sin caché de recomendaciones.

### Criterio de selección

Solo participan eventos publicados que aún no empiezan y tienen cupos. Se excluyen los propios y los que el usuario ya compró (compra pagada o reembolsada). Las compras pendientes/rechazadas no excluyen eventos ni aportan señales.

El motor es una recomendación por reglas con puntuación explicable:

| Señal | Puntos | Justificación |
| --- | ---: | --- |
| Coincidencia con uno o más intereses elegidos | 50 | La preferencia explícita es la señal principal. |
| Categoría de una compra anterior pagada/reembolsada | 30 | Representa una elección previa del usuario. |
| Categoría visitada en los últimos 90 días | 15 | Expresa exploración reciente. Repetir visitas no multiplica el puntaje. |
| Mismo distrito y departamento | 20 | Aproximación de cercanía con los datos existentes. |
| Mismo departamento, distinto distrito | 5 | Ubicación regional; no se suma a los 20 puntos anteriores. |

Los empates se resuelven por entradas vendidas, fecha más próxima e ID. Se devuelven hasta seis eventos con puntaje positivo, por lo que puede haber menos de seis.

`Interes` (Música, Tecnología...) y `Categoria` (Concierto, Taller...) son catálogos distintos: sus IDs no se comparan entre sí. La afinidad de intereses se calcula con términos completos del nombre, descripción y categoría, normalizados sin tildes ni diferencias de mayúsculas. El vocabulario de los ocho intereses iniciales está centralizado en `RecomendacionService.TerminosInteres`; un interés nuevo busca su nombre completo. Es una aproximación textual, no una medición de distancia ni un modelo de embeddings.

Cuando no existen intereses activos, compras previas ni visitas recientes, el título es **Populares cerca de ti** y se muestran los eventos con más entradas vendidas del departamento del usuario. Si tampoco hay eventos locales disponibles, se devuelve una lista vacía con un mensaje, sin inventar resultados.

### Comprobación manual

1. Iniciar sesión y guardar de uno a cinco intereses.
2. Consultar recomendaciones y verificar su motivo. Cambiar intereses y consultar otra vez.
3. Visitar un detalle con el JWT para que el flujo existente registre `EventoVisita`; volver a consultar.
4. Comprar un evento recomendado y comprobar que deja de aparecer.
5. Desde “Mis entradas”, descargar un voucher y luego el PDF de la compra completa.
6. Escanear el QR usando el check-in del organizador durante la ventana permitida. Un segundo ingreso debe rechazarse.
7. Intentar las descargas con el token de otro comprador: deben devolver 404.

Las pruebas automatizadas cubren autorización HTTP, propiedad, validaciones de intereses, exclusiones, señales de recomendación, actualización tras cambios, límite de seis, respuestas vacías y generación de PDF con textos largos y estados válidos/utilizados/anulados.
